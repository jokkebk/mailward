# Mailward v3 — architecture and implementation plan

Status: agreed direction, ready for implementation. Written 2026-09-30.

Implementation update: the v3 review path is available at `/` on the
`codex/mailward-v3` branch. The three views, bounded representation, batched Jev
assessment, review service, ledger reuse, and additive migration are implemented.
See README for use and fixture preview. A live Gmail/real Jev evaluation,
larger-representation reassessment, calibrated thresholds, and adapters remain
follow-up work. The original v2 path remains at `/v2` for comparison.

The annotated `v2` tag preserves commit `7bb4839cf2e9127565740ce222453fc8cb352827`,
the existing Jev-enabled, rule-centric application. This document defines v3;
DESIGN.md and CONTEXT.md describe the existing implementation where they differ.
Update those documents as v3 lands rather than pretending v3 is already shipped.

## Outcome

Assess each email once, then offer three interchangeable ways to review the same
results. Surface both **needs action** and **worth checking out**. Preserve the
learning embedded in current rules without requiring the user to operate twenty
rule cards. Remain a human-or-secretary-in-the-loop system; this is not a project
to build a fully autonomous email agent.

The core workflow is: fetch → deterministic representation → batched Jev
assessment → deterministic handling proposal → review → reversible execution.
The daily path stays simple. A capable agent periodically reviews feedback and
revises a compact, versioned policy; examples do not accumulate in every request.

## Scope and deliberate limits

- Implement all three review views, backed by one assessment and review state.
- Fetch full message content, but give Jev a bounded deterministic representation.
- One Jev assessment pass. No automatic request-more-content loop, generative
  summarizer, policy-writing agent, or multi-stage routing tree in the daily run.
- Retain fuller inspection for humans and secretary agents. A reviewer can
  explicitly reassess with a larger representation; this can follow the core flow.
- Separate UI from services so CLI/MCP/skill adapters can be added later. Do not
  build all those transports or a task-assignment system now.
- Keep existing reversible Gmail actions, failure isolation, OAuth handling, and
  history. Do not duplicate or bypass the execution ledger.
- Initial v3 recommendations require review. Preserve automation status/receipts
  in the model and UI, but do not inherit old rules' trust into a new classifier or
  add automatic policy promotion. Any supported automation requires explicit
  user enablement; a display slider never authorizes actions.

## 1. Input and the Jev representation

### Retrieval

The current sync requests `format=metadata` for a representative unread message,
then some AI rules fetch it again as `format=full`. In v3 request full content on
the initial fetch for messages being assessed and reuse that response. Full
includes headers; do not fetch metadata and full for the same message by default.

Keep thread-level action semantics. Represent the current unread content rather
than assuming one arbitrary message describes the entire thread. Include current
unread messages within a bounded budget, or explicitly identify omitted messages;
do not silently hide another unread request. Historical thread context is available
on inspection, not automatically fetched in full for every assessment.

Cache by account/message identity and representation version. Avoid repeatedly
fetching unchanged bodies. Store the bounded representation needed for replay;
an in-run full-content cache plus on-demand refetch is sufficient initially. Do
not turn SQLite into an unbounded raw-mail mirror. Missing body parts, fetch errors,
and unread attachments must be visible as missing evidence, not empty-success.

### Deterministic transformation

Produce a typed JSON/plain-text record containing:

- Stable thread/message IDs, sender, recipients/routing, subject, date, labels.
- Clean body text with paragraph boundaries and newest content preserved.
- Attachment filenames/types and useful link labels/destinations.
- Cheap structural signals and available conversation context.
- Content availability, clipping, omitted-history/message flags, original/retained
  sizes, and a representation version.

Decode MIME correctly, select text/plain or convert HTML without executing it,
deduplicate multipart alternatives, and conservatively remove obvious quoted
history and boilerplate. Prefer retaining uncertain content over deleting it.
Use bounded excerpts rather than blindly retaining only the first characters.
Keep limits configurable and the transformation reproducible; begin with a modest
text budget and tune from measured examples. No LLM call during preprocessing.
Do not download attachment contents or follow email links as part of this pass.

### XSS and inspection

The Jev representation contains no executable markup. Render it as escaped text,
including filenames, headers, URLs, and model-selected labels. Offer **View what
Jev saw** alongside fuller message inspection.

Rich email viewing is a separate sanitized and isolated path: no scripts, forms,
unsafe URL schemes, or automatic remote-resource loading. Review the existing
sanitizer rather than treating it as sufficient by default. Test malicious MIME,
HTML, and URL cases. Sanitizing HTML does not make email instructions trustworthy;
email content is evidence, never policy or tool authorization.

## 2. Compact policy and Jev assessments

### Versioned policy

A policy describes the user's responsibilities, interests, retention preferences,
attention requirements, and durable exceptions. Maintain an explicit size budget
(start around 1,500–2,500 tokens, adjustable with evidence). Keep question/rubric
definitions versioned as well. Avoid a generic prompt-management framework.

Bootstrap a proposed policy from `bun run scripts/rules.ts` and
`bun run scripts/review-data.ts`. Reconcile current actions, intent text, change
notes, and feedback; several legacy descriptions contradict their latest action.
Do not translate every sender rule into another independent classifier pass.
Do not silently mutate or delete legacy policy data during import.

Known learning to preserve includes actual receipts versus payment heads-ups,
cloud-team ownership of routine operational work, protection for live human
correspondence, relevant AI-tool announcements, and reminders that need to be
seen before disposal. Distinguish confirmed preferences from contradictory or
one-off decisions in the import report.

### Core judgments

Ask the same small set of questions for each thread, with explicit input references:

| Dimension | Jev type | Initial interpretation |
|---|---|---|
| Category | Choice | Sales, notification, newsletter, transaction, conversation, other |
| Attention | Choice | Act/reply, read, glance, none, unclear |
| Retention | Choice | Keep, disposable, unclear |
| Urgency | Score | Concrete levels of consequence from delaying relevant attention |
| Personal relevance | Score | Concrete levels of value given the user's interests and role |

These are attributes, not a Cartesian taxonomy. Use concrete descriptive Score
levels, not bare numbers. Where urgency does not apply, derive N/A from attention
in code. Jev does not generate explanations; render selected facts and applied
policy as short reason labels. Do not invent prose rationales.

Preserve full distributions, returned confidence, actual model identity, policy
and rubric versions, and input identity. Jev confidence describes concentration
of the distribution and differs from the probability of the winning option.
Do not present either as measured accuracy on this mailbox.

### Evidence gaps

Core choices permit uncertainty. Combine that with deterministic missing-content
flags. If useful, one bounded Choice can describe the evidence gap: sufficient,
more body, conversation, attachment, user context. It does not trigger another
call automatically. Do not build an elaborate sufficiency classifier first.

Insufficient action-relevant evidence goes to review. Category ambiguity alone
need not prevent an otherwise clear decision. An API failure or malformed result
must remain unresolved, never become a default trash or silent success.

### Request shape and performance

Pack about ten threads into one shared state, with five named questions per
thread; all dimensions are answered in the same request. Start with 3–4 concurrent
requests and token/size-aware packing. Question IDs are bookkeeping; instructions
must explicitly identify the relevant thread. Keep preferences once per batch;
account for repeated per-thread question rubrics in the token budget.

100 emails × five questions means roughly ten requests containing fifty questions
each, not five hundred network calls. UI switching, sorting, and threshold changes
reuse stored assessments. Cache on message/input, model, representation, policy,
and rubric identity. Keep time-dependent ranking fresh: apply exact date arithmetic
in code and invalidate time-sensitive assessments when their relevant context changes.

Pricing checked 2026-09-30: Jev on OpenRouter is $0.042/M input tokens, free output.
At 800–2,000 input tokens/email including rubrics plus 1,000 shared tokens/batch:

| Fresh emails | Initial requests | Input tokens | Approx. cost with 20% allowance |
|---|---:|---:|---:|
| 40 | 4 | 36K–84K | $0.002–$0.004 |
| 100 | 10 | 90K–210K | $0.005–$0.011 |

Provisional estimates: 2–5 seconds of Jev work for 40 emails; 3–10 seconds for 100;
10–30 seconds end-to-end including Gmail work, with retries potentially longer.
These are planning estimates, not benchmarks of v3. Existing September 28/29
telemetry recorded five small calls per run totaling 1.76/1.87 seconds, with whole
runs lasting 6/10 seconds. Those calls assessed 11/21 threads, not a full 100-mail
five-dimension workload. Capture actual usage/cost and stage timings in v3.

## 3. Handling, ranking, and review semantics

Use a small deterministic resolver rather than one rule per combination:

- Act/reply or read → keep visible as TODO; distinguish **Needs action** from
  **Worth checking out** throughout the UI and exported briefing.
- Glance + disposable → show before clearing, then trash on explicit review.
- None + keep → archive proposal.
- None + disposable → trash proposal.
- Material uncertainty/conflicting handling evidence → review, leave untouched.

Attention and retention can differ: a receipt may require action now and retention
later; an interesting announcement may need reading now and disposal afterward.
Store current handling separately from intended handling after completion.

Priority and confidence are separate. Obligations and urgency lead the action
queue; relevance leads worthwhile reading. Trash review puts potentially important
or consequentially ambiguous items first. Category groups can be ordered by their
highest-priority member; offer a flat ranking where strict global order is useful.
Use stable tie-breaking and keep rows in place while a user edits the reviewed set.
Priority/display sliders affect visibility or ranking only, never authorization.

Rows support Trash, Archive, TODO, and Leave untouched. Notes are optional. Add
**Done/handled** where attention was satisfied: choose its final handling explicitly,
and do not log completion as a classifier correction. Optional feedback chips can
capture already handled, someone else owns it, worth reading, actual receipt, or
show before clearing. Changing a disposition is sufficient instance feedback;
the user need not write an essay or create a new global rule.

An explicit reviewed-set submission applies mutations. No Gmail writes from row
toggles or changing views. Shared service validation applies equally to UI and
future agent callers. A model reading an item does not mean the user saw it;
show-before-clearing needs explicit reviewer acknowledgement/decision.

## 4. Three views, one session

Implement a view switcher with persisted preference and shared draft decisions:

1. **Action board:** TODO, Unsure, Archive, Trash; reason/category subgroups. TODO
   visibly separates obligations from worthwhile reading. Show-before-clearing,
   proposed actions, and applied receipts remain distinguishable.
2. **Briefing:** Needs action, Worth checking out, Show me, Needs a decision, then
   cleanup grouped by intended action/reason. The same per-email controls remain
   accessible. No generative summary is required for the first version.
3. **Exceptions:** Focus on unresolved decisions and acknowledgements, with
   expandable applied receipts. Preserve a conspicuous route to obligations and
   worthwhile reading; high confidence must not make those disappear. Initially,
   proposed mutations still await review—do not label them already handled.

Use shared row components, counts, execution state, and selection/draft logic.
Switching views must neither rerun Jev nor reset edits. Applied, failed, pending,
and undone states reflect actual ledger results. Group/individual undo remain
available. Empty views and partial runs should be comprehensible.

## 5. Shared services and persistence

Expose ordinary typed application services for assess/run status, list assessments
and briefing, inspect content/representation, submit decisions, apply actions,
record feedback, and undo. SvelteKit handlers are adapters; a later CLI/MCP/skill
can call the same services. Implement the service boundary now, not a speculative
plugin platform. Reuse the existing Gmail action/undo implementation.

Persist the minimum durable concepts: versioned policy, assessment snapshots,
review outcomes, and links to the existing run/action ledger. Keep raw assessment,
human/agent decision, and execution outcome separate. Record actor and provenance.
Review-only outcomes must be representable without fabricated Gmail actions.
Legacy rule IDs must not become fake v3 rules simply to satisfy old schema shapes.
Choose additive migrations and retain old history, undo payloads, and rule lineage.

Assessments belong to an account and a specific message snapshot. Prevent stale
or duplicate submissions; a new inbound message must not inherit an old reviewed
decision. Partial API failure must not hide successful or unresolved rows.

Assignment to Alex/agent/another team can be added later. Do not introduce
TODO-Agent as a Gmail disposition or build a delegation scheduler now. A future
secretary can use the existing TODO/archive/trash operations and prepare a briefing.

## 6. Offline learning

Preserve the daily-runner/occasional-smart-agent split. The report surface exposes
policy/rubric versions, assessment distributions, reviewer corrections, completion
events, optional chips/notes, and execution/undo outcomes. A capable agent proposes
bounded edits; it favors consolidation and replacement over appending examples.

Keep examples in a local evaluation corpus, outside the routine Jev state. Separate
held-out validation from examples used to revise the policy. Do not count skipped
items or merely completed tasks as negative classifier feedback. Record sparse
evidence honestly; current approval history is not a universal calibration score.
Policy revisions do not automatically enable automation. No scheduled learning or
self-modifying production prompts are required for v3.

## 7. Implementation sequence

### A. Contracts and migration

- Inspect actual code and tests; retain useful execution infrastructure.
- Define representation, assessment, handling, feedback, and service types.
- Add migrations and minimal policy import/reporting, preserving v2 data.
- Provide an explicit v3 entry point/mode during rollout so v2 can be compared
  without two engines acting on the same review set.

### B. Content preparation

- Reuse full Gmail responses for metadata and content.
- Implement deterministic bounded representation and availability flags.
- Secure rich viewing and add View what Jev saw.
- Test MIME selection, multiple unread messages, receipt links, clipping, failed
  body retrieval, and executable HTML/unsafe links with fixtures.

### C. Assessment and deterministic decisions

- Implement the compact policy and all core Jev dimensions in batched requests.
- Add bounded concurrency, validation, cache identity, and stage/usage telemetry.
- Implement handling/ranking and unresolved outcomes without autonomous expansion.
- Provide fixture-backed evaluation without requiring live mailbox mutations.

### D. Shared review and three usable views

- Build a shared reviewed-set store and reusable row/detail/receipt controls.
- Implement Action board, Briefing, and Exceptions views over identical data.
- Implement per-email overrides, completion, optional chips, apply, and undo via
  the shared services. Persist view preference and preserve drafts across views.
- Ensure worthwhile reading is visible and separate from obligations in every view.

### E. Learning surface, evaluation, and rollout

- Extend readable feedback export to include v3 semantics and policy lineage.
- Compare compact versus larger representations on a representative local corpus,
  including confident decisions, Finnish mail, receipts, live correspondence,
  operational ownership, and interesting announcements. Do not equate agreement
  with the old system to truth or evaluate with unavailable historical context.
- Report errors, important misses, review volume, payload sizes, cost, and timing.
- Update README, DESIGN, and CONTEXT to reflect the implemented behavior and note
  anything deferred. Provide a short manual evaluation guide for switching views.

## 8. Acceptance checks

- A run produces one reusable assessment set and three working presentations.
- Worth checking out is a first-class section, not buried in uncertain or TODO noise.
- View changes and ranking controls make no Jev calls and lose no draft edits.
- No rule-card explosion or automatic content-query loop.
- Full retrieval yields a safe, bounded, inspectable representation; missing data
  never becomes a confident empty-email decision by default.
- Mutations use shared services and remain logged, reversible, account-scoped,
  and explicit; initial v3 does not silently promote itself to automation.
- Completion, correction, skip, and Gmail execution are distinguishable in history.
- Tests cover consequential behavior: processing security, decision mappings,
  stale submissions, cache invalidation, partial failure, undo, and view invariants.
- Run `bun test`, `bun run check`, and `bun run build`; perform visual/interaction
  verification of all three views. No need to invent broad test infrastructure.

## Implementation handoff

Use an isolated Git worktree and a `codex/` implementation branch. The original
checkout contains the live local database and environment. Read existing rules
and feedback through the read-only helpers when needed; do not migrate, copy into
git, or mutate the live database as a test. Use fixture/test databases for migration
and execution verification. Live Gmail mutations are not part of implementation
testing. Implement end-to-end, make coherent commits after `v2`, and report checks
and remaining limitations. The user will interact directly with the implementation
task; use judgment for routine choices rather than reopening settled design points.
